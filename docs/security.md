# Security analysis

**Scope:** the GameStream protocol Solstice must speak, the RFB and SPICE
protocols it must consume, and the attack surface a Rust implementation of the
bridge would create. Findings are from reading `moonlight-common-c`, `Sunshine`
and `spice-protocol` at 2026-10-15, plus the published advisory record.

---

## Verdict first

> **Do not expose Solstice directly to the internet.**
>
> Put it behind WireGuard, Tailscale or an equivalent. The GameStream protocol
> was designed for a LAN behind a NAT, its pairing step is gated by a
> **four-digit PIN**, its default policy sends video and audio **unencrypted**,
> and the one mature implementation of it has accumulated two authentication
> bypasses, an out-of-bounds heap write and an unauthenticated DoS in the last
> two years. The backend protocols are no better: VNC's standard
> authentication is DES with an 8-character key, and SPICE's is RSA-1024 with
> SHA-1.
>
> A hardened Solstice *could* be exposed — §6 lists what that would take — but
> it is additional work with a real residual risk, and a VPN removes the
> entire class of problem for an afternoon's setup.

This is not a reason to avoid building the project. It is a reason to put the
listener on a private interface.

## 1. GameStream pairing

### 1.1 The PIN is four digits

Sunshine enforces exactly four decimal digits (`nvhttp.cpp:654-659`). The AES
key protecting the whole handshake is

```
K = SHA256(salt[16] ‖ pin_ascii)[0..16]
```

used as **AES-128-ECB** (`crypto.cpp:325-339`, `nvhttp.cpp:790`).

The salt is sent in the clear in the first request. An attacker who captures
step ② and step ③ of the handshake — both on **plaintext HTTP port 47989** —
has a known-plaintext-ish oracle over a **10,000-entry keyspace**. Deriving the
PIN offline is a sub-second exercise. From the PIN they can complete a pairing
of their own certificate, at which point they are a permanently authorised
client.

ECB is also the wrong mode here: identical 16-byte plaintext blocks produce
identical ciphertext, which leaks structure in the fixed-layout
`hash ‖ challenge` messages.

**The host cannot fix this by choosing a longer PIN.** The PIN is generated by
the *client* and read out to the user, and `moonlight-qt` hard-codes four
digits (`app/backend/computermanager.cpp:1006`):

```cpp
QString ComputerManager::generatePinString() {
    return QString::asprintf("%04u", QRandomGenerator::system()->bounded(10000));
}
```

The entropy source is fine; the keyspace is 10,000 and it is not negotiable
from Solstice's side. Nothing in the wire format caps the length — it is just a
query-string value — so Solstice should *accept* a longer PIN if some client
ever offers one, but it cannot plan on it.

That makes the compensating controls the whole defence:

- **Short pairing window.** Measured in tens of seconds, opened deliberately,
  with only one handshake in flight.
- **Rate limit and lock out.** A handful of failed attempts disables pairing
  until a human re-enables it. Against a 10,000-entry keyspace this is the
  difference between a speed bump and nothing at all.
- **Never accept pairing from a non-loopback, non-private source address
  unless explicitly configured.**
- **Do not run the pairing listener at all** when not actively pairing.

### 1.2 The handshake runs over plaintext HTTP

Because pairing bootstraps the TLS trust, it cannot itself use it. Everything
in §1.1 is therefore visible to anyone on the path. On a LAN that is an ARP
spoof away; on the internet it is a given.

### 1.3 Ordering and state are security-critical

Sunshine tracks `sess.last_phase` and rejects out-of-order calls
(`nvhttp.cpp:753-757` and each subsequent handler). That check is not
decoration — its absence was **CVE-2024-51738** (HIGH): *"the pairing protocol
does not validate request order and is thereby vulnerable to a MITM attack"*,
which could also crash the host without any MITM. Related:
**CVE-2024-45407**, where an attacker's certificate was persisted before the
PIN check completed, and **GHSA-36ff-frg7-492f** (HIGH, Sep 2026), *"pairing
PIN can be applied to an unintended client session"*.

Three separate CVEs in the same ~200 lines of state machine. A reimplementation
should treat the pairing session as a strict linear type: one owner, one phase
transition per request, no state written anywhere until step ④ verifies, and
the session destroyed on any deviation.

## 2. Transport security of a live session

### 2.1 Moonlight's TLS is TOFU pinning, not PKI

`moonlight-qt`'s `NvHTTP::handleSslErrors` compares the certificate in each SSL
error against the pinned server certificate from pairing, and if it matches,
calls `ignoreSslErrors(errors)`. So:

- There is **no hostname verification**, no expiry check, no chain validation.
  The pinned certificate is the whole of the trust decision.
- On mismatch the client raises `401 "Server certificate mismatch"` and
  `getServerInfo()` **falls back to plaintext HTTP** — the comment is
  *"Certificate validation error, fallback to HTTP"*, intended to support
  re-pairing.

TOFU pinning is reasonable for this threat model and is arguably stronger than
web PKI for a self-hosted box. The fallback is the weak edge: an attacker who
can force a mismatch downgrades the client to an unauthenticated channel. The
blast radius is limited (the client will not stream without a successful
pairing) but the pre-pairing `serverinfo` exchange is attacker-controllable.

### 2.2 Video and audio are unencrypted by default

Sunshine's defaults (`config.cpp:826-827`):

```
lan_encryption_mode = ENCRYPTION_MODE_NEVER
wan_encryption_mode = ENCRYPTION_MODE_OPPORTUNISTIC
```

`SS_ENC_CONTROL_V2` is always requested, so keystrokes and mouse input are
AES-GCM protected. **Video and audio are not** — on a LAN, never; on a WAN,
only if the client opts in. "Opportunistic" means a client that does not ask
gets plaintext.

For a desktop-remoting bridge this is worse than it is for game streaming. The
content of the stream is the user's screen: terminals, password managers,
email. Solstice should default to **mandatory** `SS_ENC_VIDEO | SS_ENC_AUDIO`
and refuse clients that will not negotiate them, with an explicit opt-out for
trusted LAN use.

Note the IV discipline if you do: video uses a deterministic 64-bit counter
with `iv[11] = 'V'` (`stream.cpp:1762-1776`), control uses the ENet sequence
number with `iv[10] = 'C'` (client-originated) or `'H'` (host-originated)
and `iv[11] = 'C'` (`ControlStream.c:555-567`, `stream.cpp:606-609`,
`stream.cpp:1279-1282`). These are
NIST SP 800-38D §8.2.1 deterministic constructions and they are **only safe
while the key is unique per session**. `rikey` is fresh per `/launch`; never
reuse one across sessions, and never let the counter wrap.

### 2.3 The UDP peer-binding handshake

The host learns where to send video and audio by waiting for a UDP packet whose
payload matches `av_ping_payload` — 8 random bytes hex-encoded to 16 ASCII
characters, delivered to the client over HTTPS (`nvhttp.cpp:533-535`,
`stream.cpp:1507-1515`).

Off-path, that is a 64-bit secret and fine. On-path it is sent in the clear on
an unencrypted UDP port during setup, so an observer can replay it from their
own address and have the stream delivered to them instead. The window is the
session-setup phase, since `recv_ping` latches the peer on first match and
returns (`stream.cpp:2107-2135`).

Worse, the legacy path matches a literal 4-byte `"PING"` **by source address
alone** (`stream.cpp:1499-1506`), accepted unless the client set
`ML_FF_SESSION_ID_V1`. Solstice should **not implement the legacy PING path at
all**.

### 2.4 Unauthenticated UDP listeners

Three UDP ports accept packets from anyone before any authentication:

| Port | Listener | Pre-auth exposure |
|---|---|---|
| 47998 / 48000 | ping matcher | payload compare; cheap, but it is a reachable parser |
| 47999 | **ENet** | full connection state machine, reliability windows, fragment reassembly |

ENet is the significant one. It maintains per-peer state, reassembles
fragments, and runs a retransmission timer — all before Solstice knows who the
peer is. **GHSA-c428-87f8-rrv5** (Sep 2026) is exactly this: *"unauthenticated
denial of service via short ENet control packet"*.

Also consider reflection: any UDP service that answers an unauthenticated
packet with a larger one is an amplifier. Keep pre-auth responses strictly
smaller than the request, or absent.

## 3. Post-authentication attack surface

Once paired, a client sends attacker-controlled binary into several parsers.
Sunshine's record in this area, all September 2026:

| Advisory | Severity | Issue |
|---|---|---|
| GHSA-26q2-58j6-qmvv | HIGH | improper input packet validation → **out-of-bounds heap write** |
| GHSA-6w33-pjh7-p77c | HIGH | improper validation of Unicode input packets |
| GHSA-6jvv-jqr7-m6m3 | HIGH | disabled clients bypass revocation with a derived client certificate |
| GHSA-c428-87f8-rrv5 | MEDIUM | unauthenticated ENet DoS |
| CVE-2026-32253 | **CRITICAL** | authentication bypass via improper client certificate validation |

Plus, earlier: CVE-2024-31221 (unpaired clients regain access until restart),
CVE-2024-31220 (unauthenticated arbitrary file read), CVE-2025-53095
(application-wide CSRF → command injection as Administrator) and
CVE-2025-53096 (clickjacking) in the web UI.

Reading that list as a specification of what to get right:

1. **Input packet parsing.** The `0x0206` control message is a *batch* of
   magic-prefixed records of varying length. Rust's bounds checking kills the
   OOB write class outright, but length-confusion logic bugs survive it. Parse
   with a cursor that cannot over-read, validate every length against the
   remaining slice, and reject the whole batch on the first malformed record.
2. **UTF-8 text events.** `NV_UNICODE_PACKET` is 32 bytes of attacker-supplied
   bytes. Do not assume valid UTF-8; use `from_utf8` and handle the error.
3. **Client certificate identity.** CVE-2026-32253 and GHSA-6jvv-jqr7-m6m3 are
   both "we compared the wrong thing". Identify a client by the **exact DER
   bytes of the pinned certificate**, not by subject, not by a fingerprint of a
   mutable field, not by any attacker-influenced name. Revocation must take
   effect immediately and be checked on every connection, not cached.
4. **Revocation must survive.** Unpair means unpair, now, in memory and on
   disk, with existing sessions torn down.
5. **Do not build a web UI with a session cookie.** Sunshine's worst CVEs
   (CSRF → command injection as Administrator) are in its config UI, not its
   protocol. If Solstice needs management, make it a Unix socket or a
   localhost-bound API with a bearer token, and never let it launch processes.

## 4. Backend protocol security

### 4.1 VNC / RFB

| Security type | Assessment |
|---|---|
| 1 — None | no authentication, no encryption |
| 2 — VNC Authentication | **DES, ECB, key = password truncated to 8 chars with reversed bit order** (`rfbproto.rst:471-502`). ≤ 56-bit key, no salt, no server authentication, and everything afterwards — framebuffer and keystrokes — is plaintext. Offline-crackable from one captured challenge/response. |
| 18 — TLS | anonymous TLS; encrypts, authenticates nothing, so MITM-able |
| 19 — VeNCrypt | the only sound option: TLS with x509 server certificates, sub-negotiating the auth method |
| 20 — SASL | sound where available (GSSAPI/Kerberos) |
| 5/6/13/129/130/133 — RSA-AES | RealVNC's; reasonable but proprietary-ish |

**Rule for Solstice:** refuse `None` and `VNC Authentication` over anything but
loopback or a Unix socket. Require VeNCrypt with certificate verification for
any network hop, and verify the certificate properly — do not inherit
Moonlight's habit of ignoring SSL errors. An SSH tunnel to the VNC host is the
other acceptable answer.

Note the privilege asymmetry: Solstice holds the VNC password and injects
keyboard input into a live desktop session. A compromise of Solstice is a
compromise of that desktop.

### 4.2 SPICE

The ticket scheme (`protocol.h:42-46`) is RSA-**1024** with **OAEP/MGF1-SHA1**
over a password of at most 60 bytes, with a per-connection key. OAEP itself is
sound; the parameters are dated. 1024-bit RSA is below current guidance and
SHA-1 is deprecated. More importantly the ticket is a *password check*, not a
key exchange — it provides no confidentiality for the session that follows.

SPICE's answer is a **separate TLS port**, configured independently per
channel. If that is not in use, the display, input and clipboard channels are
plaintext TCP.

Historical issues worth noting: CVE-2013-4282 (stack overflow in
`reds_handle_ticket` on a long password), CVE-2021-20201 (client-initiated TLS
renegotiation → host DoS).

**Rule for Solstice:** require the TLS port for every channel, verify the
server certificate, prefer SASL where the deployment supports it, and treat a
plaintext SPICE connection the same as a plaintext VNC one — loopback only.

## 5. Risks Solstice introduces on its own

1. **It is a privileged input injector.** The bridge converts network packets
   into keystrokes on someone's desktop. Authentication *is* the security
   boundary; there is nothing behind it.
2. **It holds every credential.** GameStream client certs and private key, the
   VNC password or client cert, the SPICE ticket. Store them with restrictive
   permissions, never log them, and zeroise key material in memory
   (`zeroize`).
3. **It amplifies.** One authenticated GameStream client becomes a full
   decode/encode pipeline. An attacker who pairs once can pin a CPU by
   requesting 4K120. Cap resolution, framerate and bitrate server-side
   regardless of what the ANNOUNCE asks for, and cap concurrent sessions.
4. **It parses untrusted compressed data.** Tight/ZRLE from the VNC side,
   QUIC/GLZ/LZ4 from SPICE. These run on data from the *backend*, which is
   normally trusted — but if the backend is a VM the user does not fully
   control, it is an inbound attack surface. Decompression bombs are the
   obvious one: enforce output-size limits.
5. **FFI undoes Rust's guarantees.** An `openh264`, FFmpeg, `spice-common` or
   `nanors` binding puts C back in the data path for attacker-influenced input.
   Keep the `unsafe` boundary thin, validate before crossing it, and consider
   running the encoder in a separate process if the threat model warrants it.
6. **UPnP / NAT-PMP.** Sunshine can punch its own holes. **Do not implement
   this.** Automatically making a service internet-reachable is a decision for
   the operator.

## 6. If it must be exposed anyway

In rough order of value:

1. **Don't. Use WireGuard or Tailscale.** Moonlight works fine over both; the
   protocol never leaves a trusted network; every finding above becomes moot.
2. If something must listen publicly, expose **only** 47984/TCP, 47989/TCP,
   48010/TCP and the three UDP ports — never the management interface, which
   should bind `127.0.0.1` or a Unix socket only.
3. **Pairing off by default.** A `solstice pair` command that opens a
   60-second window — rate-limited, logged, restricted by source address, and
   with the listener bound only for the duration. The PIN is four digits and
   client-chosen (§1.1), so the window and the lockout are the real control.
4. **Mandatory encryption.** Require `SS_ENC_VIDEO | SS_ENC_AUDIO |
   SS_ENC_CONTROL_V2`; reject clients that will not.
5. **No legacy paths.** Reject appversion-gated legacy generations, the 4-byte
   `PING`, and unencrypted control. Every legacy branch is an untested branch.
6. **Resource ceilings.** Max sessions, max resolution, max fps, max bitrate,
   max decode output size, connection and handshake timeouts everywhere.
7. **Least privilege.** Dedicated unprivileged user; systemd hardening
   (`NoNewPrivileges`, `ProtectSystem=strict`, `PrivateTmp`, `RestrictAddressFamilies`,
   a seccomp filter); no capabilities. Note GHSA-fp6g-27w5-489j (Sep 2026) —
   *untrusted GUI modules executing with Sunshine's Linux capabilities* — as
   the cautionary case.
8. **Backend on loopback.** Reach the VNC/SPICE server over loopback, a Unix
   socket, or an SSH tunnel. Never a plaintext backend connection across a
   network.
9. **Fuzz the parsers.** `cargo-fuzz` over the RTSP message parser, the SDP
   attribute parser, the input-packet batch decoder, the ENet envelope and the
   RFB/SPICE message decoders. These are the five places the CVEs above lived.
10. **Log and alert** on pairing attempts, authentication failures and session
    starts.

## 7. Summary table

| Area | Risk | Note |
|---|---|---|
| GameStream pairing | **High** | 4-digit PIN, AES-ECB, plaintext HTTP, 3 CVEs in the state machine |
| GameStream TLS | Medium | TOFU pinning is fine; the plaintext fallback is the weak edge |
| Video/audio confidentiality | **High** as specified | unencrypted by default; Solstice should make it mandatory |
| Control stream | Low | always AES-GCM with a per-session key |
| Pre-auth UDP (ENet) | Medium | reachable state machine; one published DoS |
| Post-auth input parsing | Medium | OOB write class removed by Rust; logic bugs remain |
| Client cert handling | **High** | two bypasses in Sunshine; compare exact DER |
| VNC `None` / VNC Auth | **Critical** if networked | DES-56, no channel security |
| VNC VeNCrypt | Low | with proper certificate verification |
| SPICE ticket, no TLS | **High** | RSA-1024/SHA-1, plaintext session |
| SPICE over TLS | Low–Medium | dated primitives, sound transport |
| Management interface | **High** if networked | Sunshine's worst CVEs live here |
